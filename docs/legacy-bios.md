# Legacy BIOS (CSM) boot for Windows installer media

Status: implemented in `bootable-core` for the **Linux** adapter, verified end to end against a
stub `bootmgr` in QEMU/SeaBIOS, **not yet verified against Microsoft's real `bootmgr` or on real
hardware**. Nothing in this document should be read as "BIOS boot of a real Windows ISO works".
Windows and macOS adapters refuse the option (see below).

## What was missing

Windows media is built as one FAT32 partition (GPT or MBR) holding the extracted ISO. UEFI firmware
needs nothing else (`efi/boot/boot*.efi`). Legacy BIOS needs three more things:

| Requirement | Before this change |
| --- | --- |
| MBR bootstrap code that chains to the active partition | `parted mklabel msdos` leaves the 440-byte bootstrap area all zeros (checked) |
| Active (0x80) flag on the FAT32 partition | Already set (`parted ... set 1 boot on`; PowerShell `-IsActive`) |
| FAT32 volume boot record (PBR) that loads `\bootmgr` | `mkfs.fat` writes a stub that prints "This is not a bootable disk" |
| `bootmgr`, `boot\BCD`, `boot\boot.sdi` on the volume | `bootmgr` copied and checked; `BCD`/`boot.sdi` copied but not checked |

So the Linux MBR path produced media that booted under UEFI only; under BIOS it stopped at the
`mkfs.fat` stub. (On the native Windows adapter the OS formatter writes NT6-aware FAT32 boot code
and `Set-Partition -IsActive` is already applied, so that path probably already boots under BIOS;
that is unverified and the option is still refused there until it is tested.)

## Licensing decision

Rufus gets its boot sectors from `ms-sys` (GPLv2) and Microsoft's `bootsect`; the usual open
sources are Syslinux (GPLv2+) and GRUB (GPLv3+). Bootable is Apache-2.0, and `ms-sys` embeds
boot code derived from Microsoft's. Therefore:

- **Not used:** ms-sys, Rufus, Syslinux, GRUB, or any Microsoft binary (`bootsect.exe`,
  `etfsboot.com`, `bootfix.bin`, PBRs lifted from a Windows ISO or disk). No such bytes or code
  are embedded or derived.
- **Used:** two small boot sectors written from scratch for this repository in GNU assembler,
  licensed Apache-2.0: `crates/bootable-core/assets/bios/mbr.S` (440-byte MBR bootstrap) and
  `pbr_fat32.S` (FAT32 PBR). Only *interface facts* were taken from public descriptions of how
  GRUB's and Syslinux's NT loaders start `bootmgr` (load address, entry point, registers, BPB
  fields); no code was copied. The committed `.bin` files are regenerated by
  `assets/bios/build.sh` (GNU binutils) and pinned by a unit test.

If a reviewer or counsel wants stricter provenance, the alternative is to invoke an
externally installed GPL tool (for example `ms-sys`) as a subprocess, which would not affect
Bootable's own licence but would add a runtime dependency and carry Microsoft-derived bytes.
That route was not chosen.

## Boot chain implemented

```text
BIOS -> MBR sector 0 (our 440 bytes) -> active partition's first sector via INT 13h ext (AH=42h)
     -> FAT32 PBR (our code, BPB preserved) -> root dir search for BOOTMGR -> FAT cluster chain
     -> BOOTMGR at 2000:0000 -> entered at 2000:0000
```

Contract handed to `bootmgr` (the same one GRUB's `ntldr` and Syslinux's `chain.c32 ntldr=` use):
`DL` = BIOS drive, `DS=ES=SS=0`, `SP=7C00`, the boot sector with its BPB still at `0000:7C00`,
`BS_DrvNum` (0x40) = `DL`, `BPB_HiddSec` (0x1C) = partition start LBA.

Core pieces, all in `crates/bootable-core/src/bios_boot.rs`:

- `inspect_mbr` accepts only a signed MBR with exactly one FAT32 (0x0B/0x0C) partition inside the
  disk. Any other layout is refused untouched, so a stick the writer did not create is never
  reinterpreted.
- `inspect_fat32` checks 512-byte sectors, power-of-two clusters of at most 32 KiB, FAT32 BPB
  shape, at least 65,525 clusters, and that the filesystem fits the partition.
- `build_pbr` keeps the formatter's BPB, and corrects hidden sectors, drive number, and zero CHS
  geometry. The backup boot sector is rewritten identically.
- `install` writes the PBR (and backup) first, then the MBR code, the active flag on the one
  partition, and clears the flag on the others; the disk signature (bytes 440-445) and partition
  table are preserved. `verify` re-reads and checks every one of these bytes. The Linux adapter
  runs both through the whole-disk node after the filesystem is unmounted and synced.
- `preflight_tree` requires `bootmgr` (non-empty, at most 0x7F000 bytes), `boot/BCD`, and
  `boot/boot.sdi`. It runs on the mounted source **before** any erasure and again on the written
  media. ARM64 images, which have no BIOS `bootmgr`, are refused with a clear error.

Plan-level preflight (`plan.rs`): the option requires a Windows installer image, the MBR partition
scheme, a target of at most 2 TiB, and the Linux adapter; otherwise planning fails with a specific
error. The adapter additionally refuses 4Kn drives (`/sys/block/*/queue/logical_block_size` must be
512) before erasing. The plan shows a destructive step labelled experimental.

## Option surface (what both adapters must add)

Serialized in `WriteOptions` (new field, `#[serde(default)]`, so old plans still load):

```rust
pub enum WindowsBootFirmware { Uefi /* default */, BiosAndUefi }
WriteOptions { windows, windows_partition_scheme, windows_boot_firmware, bad_block_check }
```

`WindowsBootFirmware` implements `Display` ("UEFI", "BIOS + UEFI (CSM)"), `FromStr`
(`uefi`, `bios-uefi`, `bios`, `csm`), `ALL`, and `includes_legacy_bios()`, and is re-exported from
`bootable_core`.

Required adapter work (parity invariant: both interfaces, same change):

1. **Compile fix, both apps:** `apps/bootable-tui/src/main.rs::write_options` builds `WriteOptions`
   without `..Default::default()`; add `windows_boot_firmware: ...` there. The desktop crate only
   uses `WriteOptions::default()` and compiles unchanged.
2. **CLI:** `--windows-boot-firmware <uefi|bios-uefi>` next to `--windows-partition-scheme`.
3. **TUI:** a "Firmware: UEFI / BIOS + UEFI (CSM)" cycle control and key beside the Scheme control
   in the Boot group; hit region and help text.
4. **GUI:** a "Target system" select with the two `Display` labels in the Boot group, mirroring
   the TUI order.
5. **Coupling, identical in both:** choosing BIOS + UEFI forces the MBR scheme; choosing GPT forces
   firmware back to UEFI (the core rejects the mismatch with an explanatory error, which both UIs
   must surface with the normal retry affordance). Disable the control with the core's
   "currently written only by the Linux adapter" message on Windows and macOS.
6. Show the plan's new step and the experimental wording unchanged; do not add UI claims that BIOS
   boot is verified.
7. Update the `docs/rufus-parity.md` "Partition scheme and target firmware choices" row only after
   the unverified items below are closed.

## Verification performed

- `cargo test -p bootable-core`: byte-level tests on in-memory disks (no root): MBR partition entry
  and CHS encoding, active flag set/cleared, 0x55AA signatures, disk signature preserved, PBR
  jump/code placement, BPB hidden sectors / drive number / geometry patching, backup sector, every
  single-byte corruption caught by `verify`, refusal of multi-partition, non-FAT32, oversize, 4Kn,
  large-cluster, and too-few-cluster layouts, idempotence, tree preflight, plan validation, and
  serde defaults.
- `scripts/qemu-usb-bios-smoke.sh` (no root; needs QEMU, `mkfs.fat`, `sfdisk`, mtools, binutils):
  builds a 128 MiB image with an inactive partition, formats it with `mkfs.fat`, copies a stub
  `bootmgr` (`scripts/bios/bootmgr-stub.S`, 80 KiB, spanning several FAT sectors), runs the real
  `bios_boot::install`/`verify`, and boots it as USB storage under SeaBIOS. A control run without
  the boot sectors must not reach the stub. Run locally with 1 and 2 sectors per cluster: the stub
  reported `dl=80 drv=80 hid=00000800 cs=2000 tail=OK` (entered at 2000:0000, drive and hidden
  sectors correct, last bytes of the file present). This proves our MBR and PBR logic, not Windows.

## Not verified / open items

- **Microsoft's real `bootmgr` has not been booted** from this chain: no Windows ISO was available.
  Whether current Windows 10/11 `bootmgr` accepts exactly this hand-off is derived from how
  GRUB/Syslinux start it, not observed. Needed: boot a Windows 10 and a Windows 11 x64 ISO written
  by `bootable write` under QEMU/SeaBIOS and on at least two physical CSM machines, into Setup.
- The assumed 0x7F000-byte `bootmgr` ceiling is a conservative memory bound, not measured against
  current ISOs; real files above it are refused with a clear error.
- The full Linux writer path (`parted` -> `mkfs.fat` -> copy -> `bios_boot::install` on a real
  block device) was not run because it needs root; only the in-process portions and the image-file
  equivalent were exercised. Extend `scripts/loop-write-smoke.sh` for a privileged run.
- Real BIOSes differ: USB-HDD vs USB-ZIP/FDD emulation, INT 13h extension quirks, and 64 KiB DMA
  boundaries (the PBR reads at most 32 KiB per call to avoid the latter).
- The Windows and macOS adapters were only edited to refuse the option; they were not compiled for
  those targets in this environment.

## Design for the remaining platforms

- **Windows (native):** keep `Initialize-Disk MBR`, `-IsActive`, `Format-Volume FAT32` (the Windows
  formatter supplies NT6 boot code), run `bios_boot::preflight_tree`, then verify the active flag
  and the boot sector (`bootmgr` string/jump) by reading `\\.\PhysicalDriveN` sector 0 and the
  volume's sector 0. Only then lift the plan-level refusal.
- **macOS:** after `diskutil eraseDisk MS-DOS WINDOWS MBRFormat` and `unmountDisk`, call
  `bios_boot::install` on the raw device. `/dev/rdiskN` needs sector-aligned I/O and does not
  support `SeekFrom::End`, so add an `install_with_size(disk, bytes)` variant that takes the
  capacity from the reviewed device record.
- **ISOs with their own boot code:** a future "use the installer's own boot sectors" mode could
  read `boot\bootsect.exe`-style resources from the ISO at runtime (never embedded in Bootable);
  that is a separate licence and provenance review.
