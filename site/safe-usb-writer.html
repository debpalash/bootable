Target safety · privilege boundary

The target is checked twice.

Bootable filters drives before selection, binds confirmation to a reviewed plan, and revalidates the physical device before erasure.

A drive must be eligible

The native platform adapter discovers whole removable devices. A target must be USB-attached or explicitly removable, writable, large enough for the planned operation, and separate from the running system root.

Loop devices and fixed disks are not made eligible for convenience. If an adapter cannot establish the required safety properties, the device stays out of the target list.

Erasure requires a reviewed plan

Review shows the image, physical target, strategy, dependencies, ordered operations, and permanent consequences. Opening Review does not write anything. A separate acknowledgment unlocks the final erase-and-write action.

The CLI uses a plan-specific confirmation phrase derived from the device path and serial suffix.

Identity is checked again

USB device paths can change after unplugging, reconnecting, or refreshing. Immediately before writing, Bootable discovers the target by stable ID again and compares its capacity and safety flags with the reviewed plan. Mounted child filesystems are then unmounted.

Revalidation does not replace physical inspection. Confirm the device you can see and touch before authorizing erasure.

The interface remains unprivileged

The interactive desktop app and TUI do not run their network client, catalog, image parser, or renderer as root or administrator. After review, they authenticate a fixed, protected helper that accepts the plan, checks the target again, writes, and reports progress.

  • Linux uses a root-owned helper through PolicyKit.
  • macOS uses a root-owned helper and private Unix socket.
  • Windows validates the helper under Program Files and uses an authenticated loopback channel after UAC.

The Linux CLI can also be invoked directly as root. That path still uses the same target checks and plan-bound confirmation.

Cancellation leaves an explicit result

The stop action cancels on a controlled boundary, terminates managed media tools, and flushes completed raw output. Bootable reports the target as incomplete and requiring a full rewrite.

What the safety model cannot do

No software can identify a physical USB drive for you. Bootable cannot make an untrusted operating-system image safe, guarantee firmware compatibility, or recover data after the final confirmation. Backups and physical target review remain required.
