Checksums · read-back · boot tree

Know what “verified” means.

Bootable checks the download and the written media separately. The result names what was tested and what was not.

1. Download verification

When a catalog publisher provides a checksum sidecar or manifest, Bootable associates it with the image and selects the strongest supported digest: SHA-512, SHA-256, SHA-1, or MD5. A mismatch blocks the image from being written.

If no publisher checksum is available, Bootable records the download as HTTPS-only instead of presenting it as publisher-verified.

2. Raw write verification

During a raw ISO, IMG, or RAW write, Bootable hashes the exact byte stream sent to the device. It flushes the target, reads the same byte range back, and compares SHA-256.

Compressed sources are compared after expansion. The target must match the decompressed image bytes, not the smaller archive.

3. Windows media verification

Windows installer media is a constructed filesystem rather than a raw copy. Bootable validates the source tree before erasure, then checks the finished UEFI boot files, Windows payload, split WIM sequence, and FAT32 file-size rules.

What these checks do not prove

  • They do not prove that an operating-system installation will complete.
  • They do not guarantee compatibility with every firmware or board revision.
  • A checksum proves agreement with the published digest; it is only as trustworthy as the source of that digest.
  • Read-back covers the written range. It does not certify unused capacity on a larger drive.

A failed or cancelled verification is not a warning to ignore. Treat the media as incomplete and perform a full rewrite.

Boot validation

The repository includes a separate read-only QEMU/OVMF smoke-test harness for developers. It can confirm that firmware reached a loader frame. It remains separate from physical-media verification and does not claim that setup finished.
